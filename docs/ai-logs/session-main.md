# 主线会话记录：架构与计划（session-main）

> 记录时间：2026-10-09。本文件是 FlagForge 多 agent 工作流的「主线层」日志：
> 由架构 agent 撰写，记录从题目到可执行计划的推导过程。
> 与各任务的 `TX-prompt.md`（设计指令）+ `TX-report.md`（执行回报）共同构成三层可追溯日志。

## 1. 题目解读

测试题 A（Feature Flag 与灰度规则平台）的表面是 CRUD，实际区分点埋在题面细节里：

- 「同一环境 Key 唯一」→ 要求 DB 层约束而非应用层判断
- 「对重复优先级必须采用确定性策略」→ 决策显式化 + 前后端一致 + README 写清
- 「停用时始终返回 false」「第一条命中的规则决定结果」→ 评估语义的短路顺序
- 「同一次请求中的业务变更与历史写入必须保持原子一致」→ 事务纪律
- 「不按路由数量评分」「未完成内容可以如实说明」→ 鼓励聚焦核心路径 + 诚实 scoping

结论：把工程火力集中在**评估引擎正确性、两个唯一约束、事务原子性**，而非页面数量。

## 2. 技术选型推导

| 选择 | 备选 | 决策理由 |
|------|------|---------|
| Gin + GORM + golang-migrate | chi+sqlc / Echo+sqlx | AI 辅助开发场景下训练语料最多、生成质量最稳；48h 窗口内降低翻车概率优先于展示小众技术品味 |
| Vite + React + TS + AntD | Tailwind + shadcn | 题目明说「样式不要求精美，但应有清晰的表单校验、加载状态、空状态、成功或失败反馈」—— AntD 把这四件事开箱即用 |
| 纯 SQL 迁移（禁 AutoMigrate） | GORM AutoMigrate | schema 唯一事实源 + up/down 可逆（题目要求提供迁移脚本） |
| 评估引擎独立纯函数包 | 引擎写在 service 里 | 可测性最大化：15 用例秒级跑完不碰 DB；也是题目「为规则评估的核心逻辑编写自动化测试」的最优载体 |

## 3. 十个设计决策（推导要点）

1. **优先级数字越小越高** —— 直觉顺序（#1 最先评估），UI/README 双处标注消除歧义
2. **重复优先级 = 拒绝（DB UNIQUE → 409）** —— 二级排序会让「第一条命中」依赖隐藏规则；
   拒绝最可预测、最可测、文档一句话说清
3. **JSON 类型严格匹配（"1" ≠ 1）** —— 宽松转换是 flag 平台经典事故源（PHP/JS 惊喜相等）；
   类型不匹配作为 trace 显式原因，把「为什么没命中」变成可见信息
4. **停用 = 短路（规则不评估）** —— 题目原文的最强解释；trace 单条短路记录，可观测
5. **顶层扁平属性 + 缺失即跳过** —— 缺失是正常业务态（新用户没有 vip 字段）不是错误
6. **key/environment 创建后不可变** —— key 是调用方锚点；「想改 key」= 新 flag，这是平台型产品的标准判断
7. **不做 flag 删除** —— 题目未要求；删除带级联语义（历史怎么办？），主动裁剪并写进 README 是 scoping 能力的展示
8. **service 层唯一事务边界** —— 业务变更与 history 同事务，T3a 立模式 T3b 复用
9. **不做乐观锁（last-write-wins）** —— 可选项不计分；小团队场景低频编辑可接受，写入已知限制
10. **全链路 UTC** —— TIMESTAMPTZ + 前端本地化展示，时区口径唯一

## 4. 产品亮点取舍

四个候选亮点按「边际成本 / 差异化价值」评估：

- **A 评估轨迹 Trace（采纳）**：引擎本就要产出中间状态，把 cause 语义化暴露 = 边际成本≈0；
  直接回应题目「命中了哪条规则」并升维到「为什么」—— 核心体验主张
- **B 批量模拟分布（采纳）**：一次实现复用引擎循环，成本一个端点+一个页面；
  「上线前模拟不同用户群拿到什么」是 PM/平台视角的真场景，差异化最强
- **C 历史 Diff（采纳）**：history summary 本就结构化存储（jsonb），DiffView 只是渲染层；
  把「操作历史」必做项做出质感
- **D 环境间复制（备选 stretch）**：真实平台需求但新增独立交互面；时间紧第一个砍（00-README 裁剪序）
- **百分比灰度（否决）**：需引入第三种规则类型 + 哈希分桶，扰动核心规则模型；题目明说可选项不计分，风险>收益

## 5. 任务编排逻辑

依赖最小化以换取并行度：

- 把**评估引擎（T2）**从后端主线抽出 —— 它只依赖 go module 存在，与 DB 层（T1）完全并行
- 前端（T4a/T4b）靠**契约先行 + MSW mock** 与后端并行 —— 代价是 T5 需要一次真实集成收敛
- 关键路径 T0→T1→T3a→T3b→T5；T3a 先立错误信封/事务模式，T3b 复用，避免并行 agent 产出不一致基建
- 每份 executor 提示词内嵌该任务的「AI 易翻车点」（float64 归一、PATCH 字段存在性检测、
  MSW 2.x 语法等）—— 这些是评审时最能区分「人驾驭 AI」与「AI 自由发挥」的地方
