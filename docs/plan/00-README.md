## 并行调度建议（假设可同时开多个 agent）

| 波次 | 并行任务 | 说明 |
|------|---------|------|
| 1 | T0 | 单 agent，探测环境 + 搭骨架 |
| 2 | T1 ∥ T2 ∥ T4a | 三线并行；T4a 用 MSW 按契约 mock，不等后端 |
| 3 | T3a ∥ T4b | 前端继续 mock 开发 |
| 4 | T3b | 关键路径最后一环 |
| 5 | T5 | 集成验收 + README + AI 日志归档 |

**关键路径**：T0 → T1 → T3a → T3b → T5。任何环节延误优先保关键路径。

## 时间紧迫时的裁剪顺序（从先砍到后砍）

1. 砍 D 亮点（环境复制，T3b 尾部的 stretch 段）
2. 砍前端增强体验（URL 状态保持、复制 curl 按钮等）
3. 砍 T4b 的批量模拟页（保单次评估 + Trace）
4. **永不动**：T2 评估引擎 + 测试、T3a 核心 CRUD + 409 语义、原子性历史、T5 验收 —— 这些是评分基本盘

## AI 日志三层归档规范（本题提交物要求）

题目要求「将 AI 对话记录、操作日志随项目提交」。我们的多 agent 编排本身就是展示点，
按三层归档到 `docs/ai-logs/`：

1. **`TX-prompt.md`** — 每任务的设计提示词全文（从 `docs/plan/prompts/` 复制，含版本日期）
2. **`TX-report.md`** — executor 完成后写的执行报告（每份提示词末尾有模板要求）：
   做了什么 / 关键决策与原因 / 未尽事项 / 验证命令与输出摘要
3. **`session-main.md`** — 主线会话（架构师 Claude）的设计过程记录：需求解读 →
   技术选型理由 → 十个设计决策的推导 → 产品亮点取舍

README 的「AI 使用说明」章节据此描述工作流：
**主线 agent（架构）→ 8 份结构化提示词 → 并行 executor agents → 三层可追溯日志**。
这套结构本身就是「如何工程化使用 AI 编码」的最佳证明。

## Executor 使用方式

给 executor agent（无论新会话还是 subagent）的指令只有一句：

> 阅读 `C:\Users\77230\FlagForge\docs\plan\prompts\TX-xxx.md` 并严格按其执行。

提示词内已包含：必读文档路径、交付物、硬约束、陷阱清单、验收标准、报告模板。
executor 不应自行扩大范围；遇到设计未覆盖的决策点，按提示词中的「上报而非擅自决定」原则处理。
